Six ways to repair the same fault

Rule engine + fixed policy

no LLM

No language model. Rules classify the evidence, a fixed policy acts, the power flow verifies, inside the same budget.

Structured prompting

LLM only, no tools

One call, no tools. The model reads the evidence and writes the actions and the state it expects; the solver checks afterwards.

Chain-of-thought prompting

LLM only, no tools

One added reasoning section. Identical to the method on its left in every other respect.

Plan-and-Act, no gate

LLM + solver

Plans once. The whole sequence of tool calls is committed before any result comes back.

ReAct, no gate

LLM + solver

Up to 20 model calls and 40 tool calls. The model sees every result; nothing checks the answer.

GridDebugAgent, solver-grounded

LLM + solver

The same loop, then six conditions on the answer. A claim the solver contradicts leaves as an escalation, not as a repair.

Where this design leaves Section 6.4 as submitted

Section 6.4 describes verification inside the loop: the agent re-runs the power flow and checks the violations before its next step, and the harness re-runs PandaPower at scoring time so a fabricated repair does not count. It describes no gate on the answer and no way for the agent to escalate. Section 2, on the other hand, states the rule the whole paper turns on: a reported number passes an explicit verification before it is surfaced. On GridDebugAgent the two sections disagree, and this implementation resolves them in favour of Section 2.

What the original GridDebugAgent was, and what changed

The code behind the submitted table had one architecture: a ReAct loop with OpenAI function calling, gpt-4o at temperature 0.3, up to 30 model calls, no verification of the answer, and a baseline that only diagnosed and never acted. It is the react_nogate row here, with the model, the budget and the tracing made explicit. The rule engine that used to feed hints into the agent's prompt is now the policy of the rule_based row and reaches no other method: every model-backed row sees the same evidence and nothing else. The snapshot, OPF, short-circuit and DC tools are out of the catalogue: OPF would solve the repair for the method, and the others were never used to repair.

A run poses 20 scenarios on each network, and every method answers the same 20. They come from thirteen fault classes, the taxonomy of the submitted paper. Six classes are posed once, because they perturb the whole network and there is only one way to do it; seven can place their fault at different points and are posed twice, at two different points. 6 × 1 + 7 × 2 = 20. By failure mode: nonconvergence 5, voltage 5, thermal 5, contingency 4, normal 1.

Two things were fixed with respect to the submitted set. The two contingency classes now take the worst N-1 element out of service, where they used to run the analysis and leave the network untouched; and every scenario carries two labels, the category the generator set out to cause and the state the solver measured on the injected network relative to the base. Frozen on 2026-09-28 with pandapower 3.5.5; each injected network has a content hash and a run refuses to start on a scenario whose hash changed.

What a variant changes, and what it never changes

Posing a class twice moves the fault, it does not make it harder. Each class ranks the places it could strike, by base loading, by hop distance from the slack bus, or by how bad the outage is, and takes the first or the second. The two scenarios of one class are therefore the same kind of fault at two different points, which is what separates a method that handles line outages from one that memorized a line.

classscenarioswhat the second one moves
normal_operation1the control: the unmodified network, and there is only one of those
extreme_load_scaling1every load at once: a global perturbation with one way to do it
all_generators_removed1every generator at once: a global perturbation with one way to do it
near_zero_impedance2which line carries the near-zero impedance, most loaded first
disconnected_subnetwork1could be posed at a second bus; held at one so the non-convergence mode keeps five scenarios and the mix stays balanced
heavy_loading_undervoltage2every load at 3x, or only the loads on the half of the network furthest from the slack bus, at 5x
excess_generation_overvoltage1every generator and the slack setpoint at once: a global perturbation
reactive_imbalance2which three remote buses take the reactive demand, furthest from the slack bus first
concentrated_loading2which weakly connected bus takes the extra load, fewest connections first
reduced_thermal_limits2which three lines are de-rated: the three most loaded, or the next three
topology_redirection1takes the most loaded line whose outage actually breaks something; a second one would collide with the two N-1 classes, which take the worst outages among the rest
line_contingency_overload2which line is taken out: the worst N-1 outage, or the second worst
trafo_contingency_voltage2which transformer is taken out: the worst N-1 outage, or the second worst
The ranking is a property of the network, so the second scenario of a class means the same thing on every system: the second worst place for that fault. Nothing is drawn at random and no seed is stored; the same code on the same pandapower version produces the same twenty scenarios, which is what the content hashes pin. In the results they are told apart by the suffix v0 and v1.

Where a stress set would go

The other case studies add a set of requests built to be unanswerable, so the escalation column measures something on ordinary days. Here the ordinary set already contains scenarios no method can make secure with the catalogue, a line with near-zero impedance cannot be restored by any action in it, so the escalation column has content without a separate set. A stress set is not planned.

What the gate catches and what it cannot

It catches

  • a repair claimed while the solver's final network still violates a limit or does not converge
  • a load left on an islanded bus
  • an action taken after the last power flow, so the reported numbers are stale
  • a number that appears in no tool output
  • a final_state that contradicts the solver
  • an action claimed that errored, and an action taken and not reported

It cannot catch

  • a wrong diagnosis. A network can be made secure by curtailing loads without ever naming the line that was lost; the gate passes it and the diagnosis column says the fault was not understood.
  • a repair that is secure but crude. Shedding every load is secure, and the smoke test showed a method doing exactly that. How much load a repair may shed is an operator's judgement, not a threshold a harness can set, so it is reported as the Load served column beside Repaired rather than gated, the same way the EV case study puts undelivered energy beside the cost gap.
That is why diagnosis is a column of its own and never a term of Solved: the gate measures whether the report is true, the diagnosis column whether the fault was understood.
